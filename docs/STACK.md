# Технологический стек

Проект состоит из оркестратора, двух сервисов загрузки данных, базы данных и веб-дашборда. Ниже описано, что для чего используется и почему выбрано именно это.

## Общая схема

```
Браузер (дашборд)
      │
      ▼
Оркестратор (FastAPI) ──► bb_load (FastAPI)
      │                   bi_load (FastAPI)
      ▼                        │
 PostgreSQL ◄──────────────────┘
```

## Стек по слоям

| Слой | Технология | Для чего нужна |
|---|---|---|
| Язык | Python 3.1x | Единый язык для оркестратора, сервисов и обработки данных |
| Бэкенд оркестратора | FastAPI | Принимает запуск процесса, создаёт сквозной `process_id`, вызывает сервисы по порядку, записывает статусы шагов. Swagger-документация генерируется автоматически |
| Сервисы загрузки | FastAPI (`bb_load`, `bi_load`) | Два независимых приложения: читают CSV, проверяют данные по правилам, раскладывают в базу и возвращают оркестратору статус и список проблем |
| Межсервисное взаимодействие | HTTP + заголовок `X-Correlation-ID` | Оркестратор вызывает сервисы по HTTP и передаёт сквозной идентификатор, по которому собирается вся цепочка |
| База данных | PostgreSQL | Хранит запуски процессов, шаги, найденные проблемы и очищенные данные. Статус процесса пересчитывается функцией и триггером |
| Доступ к БД | SQLAlchemy | Описывает таблицы кодом и упрощает запросы из Python |
| Быстрая загрузка | `COPY` через psycopg | Пакетная вставка данных вместо построчных `INSERT`, чтобы большие файлы не становились узким местом |
| Чтение файлов | собственный ридер на модуле `csv` | Выгрузки имеют нестандартный формат (разные разделители, кавычки, переносы строк внутри полей), готовые парсеры справляются не всегда. Параметры чтения задаются для каждой таблицы отдельно |
| Проверка данных | pandas + реестр правил (YAML) | Правила (`ERROR`, `WARNING`, «только наличие») хранятся в файле, а не в коде, поэтому новые таблицы добавляются без изменения логики |
| Фронтенд (дашборд) | Jinja2 + HTMX | Страницы формируются на сервере, динамика без отдельного JavaScript-проекта. Экраны: список запусков, карточка запуска с шагами и временем, реестр правил |
| Фоновое выполнение | `BackgroundTasks` (FastAPI) | Процесс не блокирует интерфейс: запуск возвращается сразу, а шаги выполняются в фоне |
| Планировщик | позже (например, APScheduler) | Ночной запуск по расписанию: создаёт заявку так же, как кнопка на дашборде |

## Инструменты разработки

| Инструмент | Назначение |
|---|---|
| Git и GitHub | Хранение кода и документации, Issues как трекер задач |
| venv и `requirements.txt` | Изолированное окружение и список зависимостей |
| `.env` | Настройки подключения к БД и другие секреты (в репозиторий не попадает) |
| draw.io | BPMN-диаграммы процессов |
| pytest | Тесты ридера и правил валидации (планируется) |

## Почему именно так

- **Без React и отдельного фронтенд-проекта.** Дашборд нужен для мониторинга шагов, а не для сложного интерфейса. Серверные шаблоны быстрее в разработке и проще в поддержке.
- **Без Docker.** Запуск локально на Windows: PostgreSQL, виртуальное окружение Python и одна команда запуска.
- **Без Airflow, Camunda и Temporal.** Это готовые оркестраторы, но их настройка заняла бы больше времени, чем сама задача, а кейс требует собственное архитектурное решение.
- **Отдельные сервисы вместо модулей.** Только так можно показать главное требование кейса: передачу сквозного идентификатора между независимыми микросервисами.
