# Технологический стек

Проект состоит из оркестратора, двух сервисов загрузки данных, базы данных и веб-дашборда. Ниже описано, что для чего используется, почему выбрано именно это и что уже реализовано.

## Общая схема

Сейчас (реализовано):

```
run_file.py ──► PostgreSQL ◄── dashboard.py ◄── браузер
(чтение, загрузка, проверка, раскладка)   (просмотр запусков и шагов)
```

Планируется:

```
Браузер (дашборд)
      │
      ▼
Оркестратор (FastAPI) ──► bb_load (FastAPI)
      │                   bi_load (FastAPI)
      ▼                        │
 PostgreSQL ◄──────────────────┘
```

## Стек по слоям

| Слой | Технология | Для чего нужна | Статус |
|---|---|---|---|
| Язык | Python 3.1x | Единый язык для обработки файлов, сервисов и оркестратора | реализовано |
| База данных | PostgreSQL | Хранит запуски процессов, шаги, найденные проблемы, сырые и очищенные данные. Статус процесса пересчитывается функцией и триггером | реализовано |
| Доступ к БД | psycopg 3 | Подключение, SQL-запросы и пакетная загрузка через `COPY` вместо построчных `INSERT` | реализовано |
| Чтение файлов | собственный ридер на модуле `csv` | Выгрузки имеют разные форматы (разделители `;` и `$`, кавычки, переносы строк внутри полей). Сначала обычный разбор, при повреждении запасной разбор «обёрнутых» записей. Параметры чтения задаются для каждой таблицы отдельно | реализовано |
| Реестр правил | YAML (PyYAML) | Для каждой таблицы описаны формат файла, столбцы, серьёзность (`ERROR`, `WARNING`, «только наличие»), типы, уникальность и условные правила. Новая таблица добавляется без изменения кода | реализовано |
| Проверка данных | SQL-запросы, которые собирает модуль `validator.py` по таблице `validation_rule` | Пустые значения, типы, формат дат, дубликаты ключа. Проверки выполняются внутри PostgreSQL | реализовано |
| Раскладка | SQL `INSERT ... SELECT` (модуль `stager.py`) | Перенос нужных столбцов в таблицу `stg_*` с настоящими типами, `NULL` вместо пустых значений и столбцом `process_id` | реализовано |
| Дашборд (просмотр) | встроенный `http.server`, HTML без внешних библиотек | Список запусков, шаги со временем, проблемы, первые строки чистой таблицы, состояние БД. Автообновление каждые 5 секунд. Кнопка сброса данных в демо-режиме | реализовано |
| Конфигурация | файл `.env` | Параметры подключения к БД. В Git не попадает | реализовано |
| Сервисы загрузки | FastAPI (`bb_load`, `bi_load`) | Два независимых приложения: читают файл, проверяют данные по правилам, раскладывают в базу и возвращают оркестратору статус и список проблем | планируется |
| Оркестратор | FastAPI | Принимает запуск процесса, создаёт сквозной `process_id`, вызывает сервисы по порядку, записывает статусы шагов | планируется |
| Межсервисное взаимодействие | HTTP + заголовок `X-Correlation-ID` | Оркестратор передаёт сервисам сквозной идентификатор, по которому собирается вся цепочка. Сейчас `process_id` создаётся в базе и записывается во все шаги и строки данных | планируется |
| Дашборд с запуском процессов | Jinja2 в составе оркестратора | Загрузка файла и запуск процесса из интерфейса | планируется |
| Фоновое выполнение | `BackgroundTasks` (FastAPI) | Запуск возвращается сразу, шаги выполняются в фоне | планируется |
| Планировщик | например, APScheduler | Ночной запуск по расписанию: создаёт заявку так же, как кнопка на дашборде | позже |

## Принятые решения

- **Проверки в SQL, а не в pandas.** Данные загружаются в базу как текст, и все проверки выполняются запросами внутри PostgreSQL. Так в отчёте о проблемах видно, что именно пришло в файле.
- **`psycopg` вместо ORM.** Таблицы `raw_*` и `stg_*` создаются автоматически по реестру, а `COPY` нужен для быстрой загрузки, поэтому прямой доступ к БД проще и нагляднее ORM.
- **Правила хранятся в данных, а не в коде.** Изменение правила или добавление таблицы сводится к правке YAML.
- **Без React и отдельного фронтенд-проекта.** Дашборд нужен для мониторинга шагов, поэтому страницы формируются на сервере.
- **Без Docker.** Запуск локально: PostgreSQL, виртуальное окружение Python и одна команда.
- **Без Airflow, Camunda и Temporal.** Это готовые оркестраторы, но их настройка заняла бы больше времени, чем сама задача, а кейс требует собственное архитектурное решение.
