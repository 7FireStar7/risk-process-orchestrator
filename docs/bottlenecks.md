# Узкие места и архитектурные решения

Документ фиксирует, что измерено на прототипе, какие узкие места найдены, что уже сделано и что предлагается. Цифры помечены как **измерено** или **оценка**: нерассчитанное не выдаётся за результат.

## Что измерено

Файл `cbonds_tradings_stocks`, 2000 строк, 47 столбцов. Время шагов взято из дашборда (время со стороны оркестратора) и из журнала сервиса `bb_load` (время работы самого шага).

| Шаг | Время в оркестраторе, мс | Время в сервисе, мс | Разница, мс |
|---|---|---|---|
| read | 312 | 84 | 228 |
| load | 328 | 85 | 243 |
| validate | 342 | 97 | 245 |
| stage | 339 | 99 | 240 |
| **Всего** | **1321** | **365** | **956** |

При прямом запуске `run_file.py` (без HTTP) тот же процесс на таблицах по 1999–2499 строк занимал 97–152 мс целиком (по данным дашборда).

**Вывод:** обработка данных занимает около 100 мс на шаг, а около 230–245 мс на шаг уходит на оркестрацию. На файлах такого размера основная стоимость находится не в данных, а в накладных расходах вызова.

## Откуда накладные расходы

Точная доля каждой причины **не измерена**; перечислены кандидаты.

| Причина | Где | Статус |
|---|---|---|
| Разбор YAML-реестра при каждом вызове | сервис | **устранено**: реестр кэшируется и перечитывается только при изменении файла; в тестовом окружении разбор занимал около 50 мс, быстрый загрузчик около 5 мс |
| Синхронизация правил в `validation_rule` на каждом шаге (удаление и вставка 17–47 строк) | сервис | предложение: синхронизировать только при изменении реестра |
| Новое соединение с БД на каждый вызов | сервис, оркестратор | предложение: пул соединений |
| Два подтверждения записи (`commit`) на шаг у оркестратора плюс запись проблем | оркестратор | предложение: объединить в одну транзакцию |
| Новое HTTP-соединение на каждый вызов | оркестратор | предложение: общий HTTP-клиент |
| Повторное чтение файла на каждом шаге (сервис не хранит состояние) | сервис | осознанный компромисс: шаги безопасно повторять, но файл разбирается 4 раза |

## Архитектурные решения, которые уже принимают нагрузку

| Решение | Эффект |
|---|---|
| Пакетная загрузка через `COPY` вместо построчных `INSERT` | рассчитана на большие файлы; **сравнение с `INSERT` не проводилось** |
| Проверки выполняются запросами внутри PostgreSQL по всем строкам сразу | данные не пересылаются в приложение для проверки |
| Таблицы `raw_*` и `stg_*` с индексом по `process_id` | быстрый отбор строк одного запуска |
| Шаги идемпотентны: `load` и `stage` перед записью удаляют строки того же `process_id` | повторный вызов безопасен, возможны повторные попытки |
| Сервис не хранит состояние между вызовами | можно запускать несколько экземпляров |
| Правила в реестре, а не в коде | добавление таблицы не требует изменения кода |

## Узкие места при росте данных (оценка, не измерено)

| Риск | Описание | Предложение |
|---|---|---|
| Память при чтении | файл читается целиком в память перед разбором | потоковое чтение и загрузка частями |
| Объём `raw_*` | копия каждого запуска остаётся в базе | хранить ограниченное время или секционировать по дате и `process_id` |
| Запросы по `stg_*` | таблица накапливает строки всех запусков | секции и индексы по `process_id`/дате |
| Последовательные запуски | один процесс выполняется шаг за шагом | запуск разных таблиц параллельно (шаги независимы), ограничение числа одновременных процессов |

## Предложения по приоритету

1. Синхронизировать правила только при изменении реестра, использовать общий HTTP-клиент и пул соединений (простые правки, ожидается заметное сокращение накладных расходов, величину нужно измерить).
2. Объединить записи оркестратора в одну транзакцию на шаг.
3. Потоковое чтение файла.
4. Если шаги не требуют отдельной видимости, добавить режим «выполнить все шаги одним вызовом» (меньше HTTP-обменов; цена: менее детальный таймлайн).

## Как измерить

1. Создать большие синтетические файлы: `python tools/make_demo_files.py 100000`.
2. Запустить процесс из дашборда или `run_file.py` и сравнить время шагов в карточке запуска с временем на 2000 строк.
3. Для проверки накладных расходов: сравнить сумму «время в сервисе» из журнала и «время в оркестраторе» из карточки до и после каждой правки.
4. Для сравнения `COPY` и `INSERT`: отдельный замер загрузки одного и того же файла обоими способами.
